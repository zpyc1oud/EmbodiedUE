01项目背景与实际问题

从一个游戏里的机器人，到一个必须自建的训练平台。

1.1问题起点与目标

《ARC Raiders》里的敌方机器人不靠动画驱动：它的腿在真实物理中试探、打滑、重新找平衡，玩家看到的每一步都是当场算出来的。这类表现依赖与地形的即时交互，无法靠 K 帧穷举——同一段动画换一块起伏地面就失真。代价是控制策略必须被「学」出来，于是需求落到强化学习。

项目要的是一个闭环，不只是一个能收敛的训练脚本：

01 训练

把策略训出来

  • 在物理交互中反复试错，学到可用的运动控制
  • 能稳定行走、转向、抗扰动
  • 交付物：可部署的 Policy Checkpoint
02 部署

让策略用起来

  • 训练产物接入 UE 项目，在最终运行环境中直接执行
  • 部署行为与训练表现保持一致
  • 验收：项目环境中稳定可用

关键在第二条的验收标准：不是「能加载」，而是「行为一致」。后续所有技术选择都是这条标准逼出来的。

1.2为什么 Isaac Lab 路线断在部署

最短路径是复用现成的机器人学训练栈：先在 Isaac Lab / PhysX 里训练，再迁移到 UE5 / Chaos 接入项目。实际结果是前两步成立、第三步不成立——六足机器人在 Isaac Lab 中可训练可收敛、在 PhysX 内表现符合预期，但同一策略进入 Chaos 后出现持续高频抖动，无法维持稳定步态；针对单个机器人调参能缓解个别现象，换机器人、换地形后结论就不成立。

问题定性

这不是「模型训得不够好」——策略在训练环境里是达标的。问题在于训练环境与运行环境根本不是同一套物理：同一策略 → 不同物理引擎 → 动作反馈不一致 → 部署行为偏移。

「两个引擎不一样」是一句正确但没用的话。要判断迁移是否可行，必须知道差异在哪一层。这些不是能靠调参对齐的实现细节，而是求解方式的不同：

差异层Isaac Lab / PhysXUE5 / Chaos对策略的影响
铰接体表达缩减坐标 articulation，关节自由度本身就是求解变量，父子关系由公式保证刚体 + 关节约束（最大坐标），由迭代求解器逐步满足长运动链上（六足每腿三级串联）误差沿链累积，同一组 PD 增益产生不同的关节跟踪误差
关节驱动drive 可作为隐式项进入求解器，PD 与约束同步联立drive 以约束/力的形式参与迭代同样写下一组刚度阻尼，实际力矩曲线与高增益下的稳定边界都不同
接触与摩擦自有接触生成与摩擦组合Chaos 的碰撞裕度、manifold 组织与摩擦实现相同落脚动作的支撑力与打滑倾向不同：PhysX 里「蹬地不滑」，Chaos 里可能是滑的
时间与约定米 / 右手系；自有子步策略厘米 / 左手 Z-up；引擎子步策略；四元数分量顺序不同不直接致抖，但让「对齐参数」变成一堆易错换算，每换一个机器人重做一遍

为什么 RL 策略对这些差异格外敏感

监督学习的模型只要输入分布一致；RL 策略是闭环控制器，它在训练中隐式学到了环境的响应模型，并会主动利用响应里的细微规律来省力——包括接触响应的边界与驱动的滞后。这些被利用的部分恰好是两个引擎最不一致的地方。表现出来就是：静态站立看得过去，一旦进入动态支撑切换，就在控制边界上出现自激的高频抖动。

1.3路线取舍：不解决「怎么迁移」，而是消除「迁移」

部署失败后真正的决策，不是继续修补迁移链路，而是判断是否应彻底取消迁移环节。

路线 A · 未采用

保留跨引擎迁移

PhysX 训练 → 参数对齐 / 补偿 → Chaos 部署

  • 迁移环节始终存在，风险只是被推后
  • 机器人、地形、增益一变就要重复对齐调参
  • 本质：持续为物理差异付适配成本
路线 B · 采用

基于 Chaos 建训练闭环

Chaos 训练 → 同一物理后端 → Chaos 部署

  • 训练环境即部署环境，从链路上消除迁移
  • 训练基础设施一次建设、后续持续复用
  • 代价：补齐 UE5 缺失的 RL 训练基础设施

选择路线 B，等于把不确定的「适配问题」换成确定的「建设问题」：前者每次都要重来，后者只做一次。而「缺什么」也随之变得具体——UE 是游戏引擎，没有理由自带这些，但 RL 训练一个都不能少：

缺失能力要求
请求驱动的固定步进训练时间不能由渲染帧率决定；一次控制步等于该 Step 的 step_decimation 个固定物理子步，数量落在 Session 的闭区间内。
并行仿真一个进程、一个世界内承载数百个机器人实例，且实例之间物理互不影响。
跨进程通信Python 训练进程与 UE 仿真进程之间传输批量动作与状态，格式与时序都必须确定。
Reset 语义按需重置任意子集实例，恢复到确定的默认物理状态后再施加本次采样的初始状态。
Observation / Action从物理状态中按声明采集观测，把策略输出按声明施加为关节驱动，单位与坐标系明确。
训练宿主与物理基线固定步长相关的全局物理设置必须在物理场景创建前生效，并可校验。

1.4为什么不用 UE 5.8 的 Learning Agents

既然要在 UE 里训练，一个自然的问题是：Epic 官方已在 UE 5.8 提供 Learning Agents 插件（含 PPO、与外部 Python 训练进程通信、NNE 推理部署），为什么不直接以它为框架？项目评估其源码后的结论是定位不匹配——不是它不能用，而是它为另一类问题优化，那类问题的关键约束与本项目相反。

关键维度Learning Agents 的形态本项目需要的形态
控制步与物理步 训练时用固定时间步（默认 60 Hz），并可把物理步长设为与之一致；一次 agent tick 就是一个引擎帧、也是一个物理步。 两者必须解耦：Session 固定 physics_dt 与闭区间 decimation，每个 Step 另带该区间内的 step_decimation，同一控制步内保持同一个关节目标。足式接触求解需要物理步短于控制步。当前 PhantomX 行走是物理 5 ms、区间 [1, 7]；对照 Learning Agents 时用过的固定 4 子步（50 Hz / 200 Hz）不是现役配置。
时间推进的所有权 引擎逐帧驱动，训练逻辑挂在 tick 回调上（推模型）。 训练侧持有时间：收到 Step 请求才推进固定数量物理帧，空闲时不推进训练时间（拉模型）。这样 episode 长度、reset 时机与随机数消费都由训练侧确定，可复现。
机器人语义 面向游戏 agent 的通用观测/动作类型库，逐个 agent 搭建；没有铰接机器人的驱动律、拓扑与重置分布抽象。 从 PhysicsAsset 反射拓扑，配合一份声明式机器人语义自动装配，接一台新机器人不写引擎代码；并需数百实例的显式碰撞隔离。
算法与可复现性 训练算法与训练进程由插件生态提供；配置以蓝图资产与编辑器设置为载体。插件位于引擎 Experimental 目录（0.2 版）。 沿用腿足社区标准 PPO（rsl-rl），承接 Isaac Lab 阶段的超参与观测设计经验；配置需规范化哈希并写入 manifest 与 checkpoint 绑定。

结论

Learning Agents 解决的是「让游戏 agent 在游戏节拍里学会玩游戏」；本项目解决的是「让铰接机器人在受控物理节拍里学会走路，而且训练用的那套物理就是发布时跑的那套物理」。两者在时间所有权与机器人语义抽象上要求相反，因此选择自建运行时，并把 Learning Agents 源码作为设计参考保留在 references/ 中。

02系统整体架构与模块划分

谁拥有语义，谁拥有物理，以及为什么这条线必须画清楚。

2.1一句话架构与职责边界

架构原则

训练侧拥有语义，仿真侧拥有物理，接口只传数值。再加一条推论：一份声明编译出两件东西——训练时求值用的执行器，和部署时装进制品的 plan，两者是同一个对象。

这条边界回答了一个反复出现的问题：某个东西该写在 Python 还是写在 C++？答案取决于它是「事实」还是「解释」。

内容归属理由
刚体、关节、父子关系、关节限位UE 资产（物理事实）由 PhysicsAsset 唯一确定，不应在配置里重写一遍。
哪些关节是执行器、增益多少、参考姿态、动作缩放Robot semantics 配置这是「怎么用这台机器人」的训练决策，不是资产属性。
观测清单、奖励、终止、课程、reset 分布Python Task任务数学，随任务变化，不进引擎。
动作施加、状态采集、固定步进、Slot 隔离UE Worker / Robot需要贴着物理引擎执行，且必须在物理线程节拍内完成。
帧格式、字节传输、数据布局校验Transport只关心协议，不理解机器人。

2.4UE 侧模块与依赖方向

UE 侧是一个训练宿主工程加一个插件，插件划分为七个运行时模块，另有仅编辑器加载的 UERLPolicyEditor（制品导入）。划分依据只有一条：部署时用不到的东西，不能出现在部署依赖链上。

模块用于职责
UERLInterface两者最底层 POD 类型：机器人/执行器/观测/重置/地形配置结构，拓扑描述，批量数据的 schema 与视图，plan 的数据结构与校验。
UERLProvider两者Environment 与 Robot 的抽象接口、工厂、Slot 上下文、重置批、故障码、碰撞隔离计划、批量字段绑定。
UERLRobot两者通用 SkeletalMesh 机器人实现：拓扑反射、观测计划编译、统一执行器律、动作施加、运动学换算、观测采样、接触采样、重置恢复；以及一个不依赖训练会话的部署期物理适配器。
UERLTerrain两者地形几何生成：平面、高度场、箱体阵列等基元与地形图集。地形几何从不经过协议传输。
UERLPolicy部署制品载入、plan 运行时（算子注册表的 C++ 对偶）、神经网络推理封装、通用控制循环。
UERLTransport训练帧协议、Socket 服务、JSON 与规范化哈希、批量布局编译。只管协议与字节。
UERLWorker训练Worker 生命周期与阶段机、固定步进闸门、物理前后的步进管线、Slot 池、Environment 实现（栅格隔离 / 共享世界 / 美术地图）、安全监控、视口观察与录制。

2.5配置体系

配置分三类，各自回答一个不同的问题，互不重复。其中机器人声明是 Python 代码，而不是 YAML——原因见下：

assets/robots/*.py
怎么用这台机器人
执行器（增益、力矩上限、参考姿态、动作缩放）、观测选择、重置分布
tasks/*.yaml 或 Task 声明
这次训练怎么跑
任务身份与版本、机器人资产引用、任务参数与奖励权重、Worker 与 runner 参数
environments/*.yaml
在什么地面上跑
地形来源、难度分级、基元与生成参数
机器人声明不描述质量、惯量、几何或关节限位——那些是资产的事实。

机器人声明之所以从 YAML 收敛为 Python，是因为它需要派生与正则匹配：「每条腿三节、各有固定默认角」这件事写成正则字典是一行，写成 18 个逐个列出的数值就把结构信息丢掉了；而变体（例如把整组执行器的刚度调高）在 Python 里就是一次替换，在 YAML 里则要发明一套继承语法。收敛的同时旧的机器人 YAML 被删除，不保留为覆盖层——需要不改代码做参数实验时，走已有的命令行点路径覆盖通路，而不是新开一条合并语义待定的第二来源。

预置库目前有两个成员：CartPole 与 PhantomX 六足。机器人声明只在 Python。CartPole 与 PhantomX 行走的任务、Worker 和 runner 参数在 configs/tasks/*/training.yaml；地形、追逐等其余 Task 在 Python 任务声明里组装。

运行时的合成过程是确定的：Initialize 阶段先由 UE 侧从资产反射出拓扑与字段描述符，Python 侧据此建立形状表、把它与机器人声明合并成一份可运行的机器人描述，其中动作与观测的索引关系被固定下来；然后编译出不可变的会话契约，投影成仿真侧的运行配置。整条链路上不存在「第二份机器人配置」——投影是内部产物，不是用户要维护的东西。

与此同时，用户命令行覆盖会被校验（不可配置的字段拒绝覆盖）、整份解析后配置被规范化并哈希，与 git 标识、构建标识、数据布局哈希一起写入运行 manifest。评估一个 checkpoint 时可以精确回答「它是哪份配置、哪个提交、哪套布局产出的」。

03核心功能与关键技术

把训练组织起来，把训练跑快，把能力做通用。

3.1控制帧与固定步进：从 Game Tick 到 Parallel RL Step

游戏引擎的默认时序是「引擎逐帧驱动，逻辑跟着引擎走」：一帧渲染、一帧物理，训练请求与环境规模在这套时序里没有统一语义。RL 训练需要相反的关系——训练请求驱动时间推进。

项目把时序重组为三条正交的语义：

控制步
管时间：一次请求推进一个控制帧
机器人数量
管规模：一次往返承载全部 Slot
物理帧
管计算量：一个控制步 = N × 固定步长

实现上有三个关键点。第一，引擎时间由一个自定义时间步闸门控制：只有存在已被接受的 Step 请求时才让应用时间按固定物理步长前进，空闲 tick 不推进训练时间。第二，请求被接受后剩余物理帧数被置为本次 step_decimation，物理前施加动作、窗口末采样接触并递减计数，归零时才组装回包并重新关闸。第三，同一控制窗口内动作目标保持不变（对需要每个物理帧重发的驱动方式，重发的是同一个目标而不是新目标）。

一个控制帧的完整定义

训练侧提交一次动作目标与本次 step_decimation → 仿真侧在该数量物理子步内保持该目标 → 返回一次观测。Session 内不可变的是 physics_dt 和闭区间 decimation；每个 Step 另带区间内的一个标量。PhantomX 行走任务：物理步长 5 ms（200 Hz），区间 [1, 7]，控制间隔 5–35 ms；折扣与动作变化率按参考间隔 0.02 s 标定。CartPole 把区间收成单点 [2, 2]：物理步长 1/120 s（120 Hz），控制间隔 1/60 s（60 Hz）。

3.2并行 Slot 与隔离

一次 Session 在一个 UE 世界里运行固定数量的 Slot，每个 Slot 是一个机器人实例加其任务状态。PhantomX 行走任务使用 512 个 Slot，CartPole 使用 64 个。

并行的难点不是「摆得下」，而是「互不影响」。项目把这一点定义为运行不变量：不同 Slot 的机器人碰撞与接触不能相互影响；空间上错开摆放本身不构成隔离。为此 Environment 必须声明碰撞范围，隔离由编译出的碰撞计划保证：

碰撞范围几何归属隔离手段
Slot 独立每个 Slot 拥有自己的地形几何每 Slot 分配专属碰撞通道，地形与射线查询一并隔离；上限受引擎通道数量限制。
共享世界多个 Slot 共享同一份地形几何（程序化生成或美术地图）地形作为静态世界几何共享，机器人之间通过碰撞分组保持隔离；可支持的 Slot 数量大得多。

Slot 的放置由 Environment 拥有：按行列间距生成锚点，向下射线确定地面高度与法线，得到每个 Slot 的局部地面参考系。机器人的位姿与速度观测都相对这个参考系表达，因此策略看不到 UE 世界坐标，换一张地图、换一个摆放方式都不影响观测分布。

连续地形的 8 级生成参数来自一份地形定义，与并行机器人数量分开。当前任务默认采用 Slot 独立几何，为 64 个 Slot 预设 8×8 放置网格；每个 Slot 根据同一份定义生成自己的地形实例。Run 的 resolved config 同时保存地形定义和 Slot 数，因此其中出现 64 不表示复制了 64 份地形配置。操作步骤见 docs/how-to/phantomx-robust-training.md。

3.3拓扑反射与统一执行器律

机器人的结构不是配置出来的，而是从资产读出来的：从 PhysicsAsset 与骨骼中反射出刚体、关节、运动类型、唯一解锁的关节坐标、SI 单位下的限位以及父子关系。反射只负责给出结构事实；这些名字与执行器、观测、控制模式的对应关系由训练侧决定。

动作施加侧只有一条计算路径：给定刚度、阻尼、力矩上限、目标值、当前位置与速度，算出应施加的力矩并限幅。刚度大于零时按位置目标解释，否则按力矩解释，被动关节是同一个公式的退化情形。这样做的收益是行为可预测——不存在「某个控制模式下走了另一条分支」的问题。

3.4观测体系

观测在配置里以「类型 + 目标」的形式声明，编译成固定顺序的字段，运行时按索引写入批量缓冲。可用的观测类型是一个封闭集合：

类型形状说明
关节位置 / 速度标量按关节声明，SI 单位。
刚体位姿7 维位置（米）+ 四元数（xyzw），相对所属 Slot 的地面参考系。
刚体线速度 / 角速度3 维同样在 Slot 局部参考系下表达。
离地高度标量指定刚体相对地面的高度。
接触标量 0/1指定刚体在控制窗口末、最后一个已完成 solver step 的几何支撑。只在窗口末查询一次，不累计窗口早期的支撑或碰撞事件。
接触力标量同一窗口末已完成 solver step 的净冲量按该步秒数换算得到的牛顿值。不是窗口内峰值，也不是控制窗口时长上的平均。
地形高程扫描7×5 网格以机器人根为参考、沿世界水平面建立 footprint；每个值是射线命中点 Z 减 root.Z 的米制高度。它是外感知输入，不暴露世界坐标，也不复制地形配置。

形状与语义由谁定义

这条约束消除的是一类很难查的错误：两侧各存一份「地形扫描是 35 维」这样的常量，一侧改了另一侧没改，训练照样跑，只是策略看到的东西错位了。

3.5协议与批量数据面

两侧通过本机 TCP 连接通信，同步、单请求在途。协议分成两个面：控制面用严格 JSON（初始化、拓扑、schema 协商、布局描述、manifest 哈希），数据面用协商好的二进制批量布局（动作、状态、重置）。

要素设计
帧头固定 48 字节大端头：魔数、主/次版本、消息类型、标志位、载荷长度、序号、会话 UUID、布局标识。控制载荷上限 1 MiB，数据载荷上限 64 MiB。
消息Hello / Initialize / InitialState / Ready / Shutdown 与 Step / Reset，加统一的错误消息与稳定错误码。
会话阶段两侧各有明确的阶段机，阶段不匹配的请求直接拒绝，不进入物理。
规范化哈希控制面 JSON 按规范化形式序列化后哈希，用于配置身份、schema 选择与布局标识——两侧对同一份内容算出同一个值。
批量布局五种：初始状态、动作、步进结果、重置请求、重置结果。每种由有序的命名段组成，段有 dtype 与形状，首维恒为 Slot 数，对齐与零填充被显式校验。
失败语义超时、协议错误或无法判定是否已送达的传输失败，一律视为整个 Session 失效，不重放已发出的请求。

数据面上还有两个刻意的选择。其一，段是字段主序的：每个观测字段各占一段，形状首维是 Slot 数；动作则是单段的 [Slot 数 × 执行器数]。其二，布局在初始化时协商并哈希，运行期只按偏移读写，不做名字解析。这两点共同保证了热路径上没有字典查找与字符串比较。

Reset 的表达

重置请求携带一个位掩码（哪些 Slot 需要重置）、每 Slot 的地形难度等级、以及重置目标值矩阵。仿真侧先恢复初始化时为每个 Slot 捕获的完整默认物理状态，再施加本次的覆盖值——不存在「部分重置」的降级路径。

要让两侧真的等价，机制上做了三件事：

  1. 算子集是封闭的。取字段、拼接、按四元数逆旋转到机体系、重力投影、命令通道注入、控制帧时长、上一帧动作、关节位置相对默认姿态、缩放、偏移、裁剪——大致就这些。声明层负责把「相对默认姿态」这类语义展开成带具体参数的通用算子，plan 层保持最小。PhantomX 把 control_frame_dt（秒 × 100）编进观测，策略才能在可变控制间隔下工作。
  2. 新增算子有准入规则。Python 实现、C++ 实现、一致性语料和负向自检必须同一变更集落地。细则在 engine/Plugins/UERLEngine/Source/UERLPolicy/Docs/Operators.md。
  3. 一致性由共同语料裁定。语料是版本控制里的数据（plan、原始状态、命令、期望输出、容差），Python 测试与 UE 自动化测试读同一份语料，各自与期望值比对——不是一侧对另一侧负责，而是两侧对同一个提交进仓库并经过评审的常量负责。

而奖励、终止、事件、课程这些不进部署路径的部分，则完全不受算子约束，可以是任意 Python 实现。这条分界让「表达力」与「跨语言可验证性」各自落在需要它们的地方。

只有一条任务路径

任务侧刻意没有「抽象基类 + 声明式实现」两套东西：由 manager 装配的声明式任务就是唯一的任务类型，导出器直接从这个任务对象上读取两个 plan，中间不存在任何转接层。理由与算法侧一致——为唯一的实现留接缝，是在为不存在的第二个实现付代价，而两条路径共存的直接后果就是「plan 到底以哪一份为准」这类问题。

反过来，确实存在多个实现的地方就保留接口：命令来源目前有空来源、课程聚合来源与两种外部命令来源同时在用，因此它是真接口，不是间接层。判据是实现计数，不是风格偏好。

3.8场景随机化与 sim2sim 泛化

训练在程序化地形上进行，最终运行环境却是美术做的关卡地图。两者同属一个物理引擎，但场景几何完全不同——这是 sim2sim 泛化问题：物理没变，场景变了。它是「训练即部署」在场景维度上的最后一段。本节数值来自物理时间目标修改前的历史实验，只说明当时的评测与消融过程；新目标的策略效果需要从新 Run 训练后重新评估。

先建立基线，再改训练

这件事最容易犯的错是「先加随机化，再看效果好不好」——因为「好不好」没有尺子。所以顺序被固定为：先在美术地图上量化现状，再动训练。评测入口本身是交付物的一部分：固定地图、固定起点、固定目标轨迹、固定随机种子，输出四项指标。

指标定义
存活时长倒地前的存活秒数。
追击成功率在给定时限内接近目标到停止距离内的比例。
平均根高机身平均高度，偏低说明姿态在崩坏（腿撑不起来）。
非足端接触率非足端刚体接触地面的时间比例，用于捕捉「靠身体蹭着走」这类退化。

可重复性先被验证：同一策略重复评测两次，四项指标的抖动均为 0（约定上限 1e-5）。这一步不能省——如果评测抖动大于策略之间的差异，后面所有结论都无意义。

判据的刚性：逐项比较，不取平均

现役训练把地面摩擦随机化和根部推力扰动表达为事件 term；地形起伏来自初始化时生成的等级区域，并由课程在 reset 时选择，不在运行中重采样地形参数。历史实验按「四项指标逐项不低于基线」验收。当前 uerl play 输出评测指标，基线报告需要另行逐项比较，命令不会接收基线报告并自动返回验收结论。

为什么不取四项平均

取平均能让「三升一降」看起来像「总体改善」，而降的那一项恰好可能是姿态崩坏。判据的刚性不是形式主义：一旦允许用平均掩盖单项退化，评测就从「验证」退化成「找一个能过的说法」。

实际过程：一次真实的退化定位

加入随机化后的前两次实验都没有通过：平均根高低于基线。由于评测抖动为 0，可以确定这不是测量噪声，而是策略真的变差了。随后做单变量消融：

当时的退化来自一个不太直观的耦合：从已有 checkpoint 续训时，网络参数与观测归一化的统计量在同时漂移。随机化让观测分布本身变宽，统计量随之更新，而策略是按旧统计量学出来的——两者同时移动，策略在美术地图上的姿态就塌了。该次实验保留 checkpoint 中的归一化对象与统计量，并在续训开始后冻结其更新；这个结论不能替代新目标的从头训练与评估。

历史实验结果

使用三个随机化事件 term、固定种子、64 个 Slot、100 次迭代训练出的策略，在固定美术地图上四项指标逐项不低于基线：存活时长与追击成功率、非足端接触率持平，平均根高从 0.13412 提升到 0.13627。两次重复评测抖动为 0，严格验收通过。基线与验收标准全程未被调整。

这一节的方法论价值大于数值本身：先量化、再改动、逐项比较、退化就做单变量消融，而不是把参数调到能过为止。

3.9部署制品与游戏内推理

训练产物不是一个裸权重文件，而是一个自带解释方式的策略制品：

// 制品容器
magic        "UERLPOL2"      8 字节
format_ver   uint32
json_length  uint32
json_bytes   观测 plan / 动作 plan / 任务与机器人标识 / ArtifactTiming（physics_dt 与 decimation 区间）/ 运行元数据
onnx_length  uint64
onnx_bytes   训练框架导出的 ONNX 模型（原样承载）

制品刻意不保存网络层宽、层数、激活函数、权重、观测归一化参数与确定性输出变换——这些已经在导出的计算图里，重复描述只会带来第二个真相。制品只做一件事：把「我们的 plan」和「框架导出的网络」绑在一起，并在读入时校验观测 plan 的输出宽度等于网络输入维、网络输出维等于动作 plan 的策略宽度。

游戏内的控制器因此变得很薄：载入制品 → 编译两个 plan → 绑定机器人物理适配器 → 每个控制周期执行「采集状态 → 观测 plan → 网络推理 → 动作 plan → 施加关节命令」。宿主侧的任务专属代码收缩到三件事：用哪个制品、在哪张地图上启用、命令怎么算。控制器配置里没有执行器与观测的枚举字段——它们全部从制品推导，因此「配错」这件事在接口上无法表达。

3.11可复现性与故障边界

训练是长时间、随机性重的过程，因此「出了问题算谁的」必须在设计时就分好类。项目只承认两种故障：

故障类别范围处理
Slot 故障只破坏一个 Slot 的物理状态（非有限数值、约束失效、越出地形边界等）该 Slot 的状态标记为无效，任务侧不在其上做数学；可通过显式的稀疏重置尝试恢复。
Session 致命故障破坏协议、资产、执行计划、固定帧关系或 Slot 隔离停止整个 Session。不自动重试，不降级为「任务终止」。

表 3-9　故障分级

可复现性由几件事共同保证：配置规范化哈希、运行 manifest（含解析后配置、生效的 Worker 配置、构建标识、schema 与布局哈希、git 标识）、确定性的随机流标识、以及固定不变的控制帧关系。项目纪律要求 checkpoint 必须与产出它的提交、未提交差异、解析后配置、manifest 和评估结果绑定——否则它只是一个权重文件，不是一个结果。

验证分层也遵循同样的思路：Python 单测覆盖配置、机器人描述合并、各 manager 与 plan；协议测试用独立的 wire 实现作为对照，检查帧头、严格 JSON、布局哈希与非法输入；一致性测试用共同语料裁定跨语言等价；端到端测试拉起真实的 UE 进程跑完整链路；UE 自动化测试覆盖 Slot 隔离、地形归属、拓扑反射与接触采样。缺少外部依赖时测试返回失败而不是静默跳过。

4.2训练

训练由 Python 侧发起：解析配置 → 拉起 UE Worker 进程（或附着到已运行的进程）→ 握手、初始化、就绪 → 进入 Step/Reset 循环。可复现的任务、Slot 数和设备写在仓库 README.md；未写出的字段来自 configs/tasks/*/training.yaml。命令行点路径覆盖会被校验并计入配置哈希。运行过程中会产出 checkpoint、日志与运行 manifest。manifest 把这次运行的配置身份、构建身份与数据布局身份固定下来，用于后续复现与结果比较。

4.3评估与录制

评估复用同一套 Session 与同一份任务定义。比较新训练目标时，应明确选择新目标 Run 的 checkpoint；latest 只按时间选择，不区分历史目标。PhantomX 的机身高度振动频率按每个已完成控制窗口的实际物理时间计算。录制走视口呈现：UE 内部输出原始像素流，编码为 MP4。训练默认不显示画面，这既是性能考虑，也保证录制与否不改变物理频率。命令见 README.md 与 docs/how-to/record-video.md。

4.4导出与游戏内部署

这一步是「训练即部署」真正落地的位置。导出命令在 README.md。导出时会校验制品自洽：观测 plan 的输出宽度等于网络输入维、网络输出维等于动作宽度、运行时执行器与命令字段逐一对应。运行时执行器参数由 Python 机器人声明生成，不手写第二份。

制品放入 UE 项目后，游戏内的部署路径不再涉及 Python、不涉及协议、不涉及 Worker：把 BP_UERLPolicyRobot 放进关卡，或把 UUERLPolicyComponent 接到已有 Skeletal Mesh。蓝图提供命令通道，插件完成观测、ONNX 推理和关节驱动。接到另一份工程的步骤在 docs/in-game-deployment-guide.md。宿主 Egypt 关卡是演示玩法，不是插件接口。

4.5场景泛化训练与评测

与 3.8 对应的顺序是先评测，再改训练。先在 UERL-PhantomX-Pursuit-v0 上评测，再从新 Run 训练 UERL-PhantomX-ContinuousTerrain-v0，然后用同一评测入口取得报告并逐项比较。入口就是 README.md 里的 uerl play 与 uerl train。固定美术地图评测走追逐任务；事件 term 提供摩擦与根部推力扰动，地形等级由课程选择。消融一次只覆盖一个点路径（事件权重或观测归一化），不同时改训练入口、评测入口和基线。

4.6验证

基础验证与完整门禁命令见仓库 README.md 与 tests/README.md。Python 单测不启动 UE；UE 变更还须编译 UERLHostEditor Win64 Development，并跑与本次切片相关的 Automation / E2E。缺少外部依赖时测试返回失败而不是静默跳过。第 3.10 节的性能数字来自当时的实测闭环，不是每次提交都重跑的门禁。
